# Наблюдения за Bohemia lobby API

Журнал фактов с живого API. Дата, что наблюдали, что из этого следует. Гипотезы помечены явно.
Связанные открытые вопросы — ADR 0004 (идентичность сервера), AGENTS §26.

## 2026-09-10 — первый живой запуск `cmd/probe`

Сервер `37.48.253.41:2001` («[RU] #1 | ARMA-RUSSIAN.RU»), клиент 1.8.0.13.

**rooms/search по hostAddress**
- Вернул ровно одну комнату, `totalCount=1`, `searchFrom=0` совпал с запросом. Гипотеза «несколько комнат на адрес» пока не подтверждена; `Limit: 5` оставлен как страховка.
- Полный набор полей комнаты при `lightweight=false` (26 ключей): все поля из AGENTS §3.1 плюс `detailsUpdatedAt`, `favorite`, `flags`. Добавлены в `bohemia.Room`.
- `roomId = 34008e3e-9a0c-4be0-b94f-c7f3cb547626` — **тот же**, что в fixture от 2026-09-03 и в AGENTS.md. Минимум неделю roomId не менялся. Либо сервер не перезапускался, либо roomId переживает рестарт. Требует целевого эксперимента: снять roomId до и после известного рестарта.
- `directJoinCode`: 2026-09-03 было `0956251811`, сейчас `0245999839`. **Меняется в пределах недели** → не годится как identity key (ADR 0004, кандидат понижен).
- `sessionId = c134568a-000051ffebe3` — формат отличается от UUID; сравнить при следующих запусках.
- `hostType = CommunityDs`, `official = false`, `battlEye = true`, `platformName = Windows`, `pingSiteId = frankfurt`.
- `supportedGameClientTypes = [PLATFORM_PC, PLATFORM_XBL, PLATFORM_PSN]` — кроссплатформенный сервер.
- Два таймстампа: `updated` (heartbeat, менялся) и `detailsUpdatedAt` (описание).
- `mods = []` — форма элементов по-прежнему неизвестна, нужен модовый сервер.
- Очередь: `joinQueue = {type: REGULAR, size: 19, maxSize: 50, positionAvgWaitTime: 70}`.

**rooms/listPlayers**
- 128 connected + 19 queue, числа совпали с `playerCount` и `joinQueue.size` из search.
- `gameClientType` не только `PLATFORM_PC`: наблюдались `PLATFORM_PSN` (platformUserId — 19-значное число) и `PLATFORM_XBL` (40 hex-символов). Подтверждает ADR 0006: `platform_user_id` — текст, без предположений о формате; `game_client_type` обязателен в ключе маппинга.
- Bohemia `userId` — UUID для всех платформ.

## 2026-09-10 — пагинация и полный скан (вечер)

- В лобби ~**5050** серверов (`totalCount` колебался 5050–5051 между страницами: серверы приходят и уходят во время скана → upsert, дубли/пропуски на границах страниц допустимы).
- `limit` до **500** принимается (проверены 50/100/200/500). Ответ ~7 КБ на комнату, страница из 500 ≈ 3,7 МБ. Полный скан = 11 запросов, ~35 МБ, каждый < 1 с. `maxBodySize` 8 MiB хватает для 500, для 1000 не хватит.
- `from=50` → `searchFrom=50`, пагинация работает как ожидалось.
- **`lightweight=true` ничем не отличается от `false`**: одинаковые 28 ключей, включая `mods`, `joinQueue`, `runtimeStats`. Флаг оставлен в запросе, но экономии не даёт.
- Объём ответа определяют `mods`: до 179 модов на комнату, 23 из 30 серверов страницы модовые.
- **Форма `mods`**: `{modId: "5F0D245931200FD1", name, version}`. Добавлен тип `bohemia.Mod`.
- Ещё два поля комнаты: `hostedScenarioModId` (мод со сценарием) и `lastJoinedAt` (unix, не у всех). Добавлены в `Room`.
- **`sessionId` не уникален**: `0-000000000030` у 22 из 30 комнат (похоже на «нет значения»), `c134568a-000051ffebe3` у **двух** комнат, одна из них наш тестовый сервер. Гипотеза: sessionId относится к хосту/процессу, обслуживающему несколько комнат, а не к серверу. Как ключ идентичности сервера **не годится**; как ключ группировки «комнаты одного хоста» — возможно, проверить.
- `hostAddress` присутствует у всех 30 комнат.
- `flags` = 1 у всех, `hostType` = CommunityDs у всех в выборке.

## 2026-09-10 — первые два полных скана в БД (`cmd/observer`)

| Скан | Комнат | Новых серверов | Деактивировано | Время |
|---|---|---|---|---|
| 1 | 5050 | 5049 | 0 | 11,6 с |
| 2 (через 30 с) | 5054 | 7 | 5 | 10,7 с |

- За 30 секунд между сканами 7 серверов появились, 5 исчезли — лобби живое, суточный скан даст только грубую картину «существует ли сервер»; точная история онлайна — из минутного tracking.
- **Один hostAddress, две комнаты в одном скане** (`103.45.128.9:2001`, одинаковое имя): upsert по адресу схлопнул их в один сервер, оба снимка сохранены. Пока единичный случай; природа неясна (перерегистрация во время скана?).
- **sessionId**: `0-000000000030` у 2539 из 5050 комнат — заполнитель «нет сессии», как ключ бесполезен. Остальные группируют комнаты: `9f88ed4d-…` — 8 комнат одного IP, `c6b0b500-…` — 6 комнат одного IP, но `9a18d5ce-…` — 7 комнат на **7 разных IP**. Гипотеза: sessionId — идентификатор процесса/хостинга, обслуживающего несколько комнат, а не физического хоста. Для merge-подсказок может пригодиться как слабый признак «комнаты одного оператора»; хранится в `server_identity_key` как история.
- **Распределение онлайна** (скан 1): 4053 пустых, 788 с 1–9 игроками, 125 с 10–49, 84 с ≥50. Всего 13 612 игроков и 605 в очередях. Для `tracking_enabled` кандидатов «с реальным онлайном» ~200 серверов.
- Топ по онлайну: 128/128 с очередями 25–45, регионы frankfurt/london.
- **Объём**: raw payload одного скана ~16 МБ (в jsonb 17 МБ на диске); 14 дней retention ≈ 240 МБ. `server_observation` — ~2 МБ на скан. Приемлемо.
- Скан с `pageSize=500` укладывается в 11–12 с, из них Bohemia отвечает <1 с на страницу; остальное — 500 комнат × 5 запросов к Postgres в транзакции. Оптимизация батчами не требуется для суточного цикла.

## 2026-09-10 — первый прод-запуск tracking (~110 серверов)

- Обход ~110 серверов с равномерным распределением стартов работает; второй обход показывает реальную динамику (joined/left/suspected единицы на сервер за минуту).
- **`listPlayers` → HTTP 400** для части комнат (≈3 из 110), при том что `rooms/search` их отдал. Причина неизвестна — тело ответа не сохранялось. С этой версии тело HTTP-ошибки пишется в `poll_run.error_message`; проверить, что общего у этих серверов (`password_protected`, `joinable`, `visible`, `official`, `hostType`).
- `ROOM_NOT_FOUND` для ≈2 из 110: сервер есть в каталоге, поиск по адресу пуст. Ожидаемо при рестарте; состояние игроков не трогается.

## План хранения (согласован 2026-09-11, реализация отложена)

Диск на проде ~10 ГБ. После нескольких дней сбора статистики и проверки, что Bohemia не ограничивает опросы:
1. raw payload — только от суточного скана; ответы минутного опроса не хранить (или флагом на пару дней).
2. `server_observation` из tracking — только при изменении описательных полей + контрольный снимок раз в 10 минут.
3. `poll_run` — 7 дней подробно, далее суточная статистика по серверу.
Оценка: ~5 ГБ/год при 200 серверах. Пока — временно `RAW_RETENTION=48h` в deploy/.env.

## 2026-09-11 — listPlayers с чужим roomId

| roomId | Ответ |
|---|---|
| несуществующий UUID | **404** `{"code":404,"apiCode":"MpRoomNotFound","message":"There is no room …"}` |
| мусор `not-a-uuid` | 404, тот же `MpRoomNotFound` |
| roomId тестового сервера от 2026-09-03 | **200**, 39 игроков — roomId живёт уже ≥ 8 дней |

Выводы:
- Устаревший roomId даёт явную ошибку, а не пустой список → безопасна оптимизация «сначала listPlayers по сохранённому roomId, rooms/search раз в N минут и при 404». Экономит до половины запросов к Bohemia. **Отложено** до анализа суточной статистики.
- Клиент классифицирует такой 404 как `ROOM_NOT_FOUND` (по `apiCode`).
- roomId тестового сервера не менялся ≥ 8 дней: гипотеза «меняется при каждом рестарте» пока не подтверждается.

## 2026-09-11 — причина HTTP 400 на listPlayers (прод)

`{"code":400,"apiCode":"InvalidInput","message":"Room is password protected but password or inviteToken wasn't provided."}` —
запароленные комнаты не отдают игроков чужому аккаунту. В игровом клиенте есть фильтр «только без пароля»;
имя поля в теле `rooms/search` пользователь снимет через прокси (не угадывать). После этого: поле в `searchRoomsRequest`,
запароленные — вне выборки tracking.

**Следующие проверки**
- roomId после рестарта сервера (нужен сервер с известным временем рестарта или наблюдение за `sessionId`/`updated`).
- sessionId: проверить, сохраняется ли он у сервера после смены IP (тогда это сильный признак для merge) — нужна история за недели.
- Случай двух комнат на одном hostAddress: повторяется ли, что у них с roomId/updated.
- Порядок `queuePlayers[]` — соответствует ли позиции в очереди.
